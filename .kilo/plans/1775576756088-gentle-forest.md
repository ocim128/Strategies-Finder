# Review: Finder Stop Button & Live Results

## Summary of Changes
- Added `isCancelled` flag + stop button to `FinderManager`
- Added `isCancelled()` and `onResultsUpdate()` to `FinderRunCallbacks` interface
- All runners (single, multi, polymarket, genetic) check cancellation at loop boundaries
- Live results are pushed to UI during run via `onResultsUpdate` callback
- `tests/lib/` mirrors updated identically (confirmed binary-identical copies)

---

## Issues Found

### BUG (High): Indentation regression in `finder-runner-single.ts:1515-1527`

The Rust batch-processing path at the bottom of `runSingleTimeframe` has broken indentation. Lines 1516-1526 are indented at 12 spaces instead of 8, making the code structurally inconsistent with the rest of the file and with the parallel non-Rust path at lines 1427-1439.

**Before** (original, 8-space indent):
```ts
        processedCount += batchJobs.length;
        if (shouldUpdateUi(processedCount === totalRuns)) {
            ...
        }

        await maybeYieldByBudget(true);
    }
```

**After** (current, mixed indent):
```ts
        processedCount += batchJobs.length;
            if (shouldUpdateUi(processedCount === totalRuns)) {  // 12 spaces!
                ...
            }
            await maybeYieldByBudget(true);                        // 12 spaces!
    }
```

The code still runs correctly since JS/TS doesn't care about whitespace, but it's a regression that will confuse maintainers.

**Fix**: Re-indent lines 1516-1526 back to 8-space indent to match the rest of the while-loop body.

---

### BUG (Medium): Missing `onResultsUpdate` throttle in single-timeframe runner

In `finder-runner-single.ts`, both the non-Rust path (line 1436) and the Rust path (line 1524) call `onResultsUpdate` every time `shouldUpdateUi` returns true (~every 250ms). This triggers `sortFinderResults` + `renderResults` (full DOM re-render) up to 4 times per second.

The multi runner (`finder-runner-multi.ts:217-228`) and polymarket runner (`finder-runner-polymarket.ts:417-422`) both have an explicit 750ms throttle via `lastResultsUpdateAt`. The single runner lacks this.

**Impact**: Unnecessary DOM churn during single-timeframe runs. May cause visible jank on large result sets.

**Fix**: Add the same 750ms throttle pattern to the `runSingleTimeframe` function.

---

### UX Issue (Low): Progress bar not hidden on cancel

When the finder is stopped by the user, only the status text is updated. The progress bar stays visible at its last percentage:

```ts
if (this.isCancelled) {
    this.setStatus(`Finder stopped by user after ...ms.`);
    // setProgress NOT called — bar stays visible at last %
} else {
    this.setStatus(`Finder completed in ...ms.`);
    this.setProgress(false, 100, "");  // this hides the bar
}
```

`setProgress(false, ...)` sets `container.classList.toggle("active", false)` which hides the progress container. On cancel, the bar remains visible indefinitely.

**Fix**: Add `this.setProgress(false, 0, "")` in the cancel branch, or call it unconditionally in `finally`.

---

### Observation (Low): Double sorting in `onResultsUpdate` callback

`finder-manager.ts:770-774`:
```ts
onResultsUpdate: (results: FinderResult[]) => {
    const sorted = sortFinderResults(results, options.sortPriority);
    ...
}
```

All callers already pass `ranker.toSortedArray(topN)` which returns sorted results. The callback re-sorts with `sortFinderResults`. This is redundant but harmless (sorting an already-sorted array is fast). Not a bug, just unnecessary work.

---

### Observation (Low): No live results during genetic optimization

`runGeneticFinder` only calls `onResultsUpdate` on cancel (line 54), not during normal generation progress. The `onGeneration` callback updates progress/status but doesn't push results. This means the genetic runner shows progress but no intermediate results — unlike single/multi/polymarket runners.

This is arguably acceptable since genetic search only produces one result per strategy (the best genome), but it's inconsistent with the other runners.

---

### Observation (Low): Genetic optimizer has no inner-loop cancellation

`runGeneticFinder` checks `isCancelled()` only between strategies (line 51). Once `runGeneticOptimization()` starts (line 64), the stop button has no effect until that strategy's optimization completes. For long-running genetic searches, this could mean a significant delay before the stop takes effect.

---

## Non-Issues (Verified OK)

- **`isCancelled` thread safety**: JS is single-threaded; the click handler sets the flag, the runner reads it after `yieldControl()` — correct pattern.
- **`finally` block cleanup**: `isCancelled` is reset in `finally` (line 807), preventing stale state if the user clicks stop while not running.
- **`FinderRunCallbacks` interface**: Updated in both `finder-runner.ts` (main) and `finder-runner-single.ts` (local copy) — consistent.
- **DOM contract**: `stopFinder` id added to both HTML partial and `finder-manager-dom.ts` — contract is aligned.
- **CSS**: `.finder-actions` layout looks correct with flex gap.
- **`tests/lib/` files**: Binary-identical to `lib/` counterparts — correctly kept in sync.

---

## Recommended Actions

1. **Fix indentation** in `lib/finder/finder-runner-single.ts:1516-1526` (8-space indent)
2. **Add 750ms throttle** for `onResultsUpdate` in `runSingleTimeframe` (matching multi/polymarket pattern)
3. **Hide progress bar on cancel** in `finder-manager.ts` (add `setProgress(false, ...)` in cancel branch)
4. Items 4-6 are optional improvements, not regressions
